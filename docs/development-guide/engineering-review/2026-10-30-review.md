## Rejections and deferrals: accept or challenge

The 29 Oct Completed page gave a reason for each rejection and deferral. This table gives the verdict on each.

### Rejected

| ID | Decision (29 Oct) | Verdict | Reason |
| :--- | :--- | :--- | :--- |
| SEC-03 | Rejected: keep SHA-1 ESXi thumbprints | **Accept the outcome. Challenge the reason.** | The stated reason is that SHA-1 is not collision-resistant. A pin does not need a collision. An attacker must find a certificate with the same SHA-1 as the pinned one. That is a second-preimage attack, which is still infeasible. The real reason is that the thumbprint is what the host provides. The pack already requires SHA-256 for the vCenter REST pin (`tls.normalize_thumbprint` and the 64-character check in `collectLibraryData.py`). So the "limit of what vCenter provides" needs a check on the test instance: does the ESXi path accept SHA-256? If yes, the rejection should be revisited. Rewrite the reason in `2026-10-29-completed.md`. |
| SEC-05 | `defusedxml` not adopted | **Accept.** | The input is written only by VCF Operations administrators. A new runtime dependency would need its own audit. The `nosec` markers now name the reason, and bandit is clean (see N-02 for the audit scope). |
| GOV-04 | No changelog file | **Accept.** | The reviewer's own correction. The project uses GitHub release notes. |
